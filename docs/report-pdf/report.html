01 Crash & state fixes

C1 Completed trips reappear

BeforeAdmin polling every 5 seconds overwrote progress with the full roster.
AfterThe server roster is accepted once per session. Fetch Roster = a fresh snapshot. During a shift, local progress is not overwritten by polling (design decision).
ScheduleActivity.kt · ScheduleViewModel.kt

C2 Items lost on cancel / crash

BeforeThe item was removed and the cache written before the driver committed.
AfterRemoval is only staged. The cache is written on RESULT_OK. On cancel, the list is restored.
ScheduleActivity.kt

C3 Trip completed, process died, trip repeated

BeforeIf the process died before RESULT_OK arrived, the trip came back.
AfterMap, REP, Break, and Signing write the cache themselves the moment the item completes (ScheduleCache).
ScheduleCache.kt (new) · Map/Rep/Break/Signing Activity

C4 REP given the Sign On placeholder route

BeforeThe depot→depot REP and the Sign On placeholder share the same terminals, and the matcher took the first one.
AfterThe route at the roster item's position is preferred, including for a trimmed roster (cache mode).
RouteMatcher.kt (new) · ScheduleActivity.kt

C5 Silently used the first route

BeforefirstOrNull() fallback, so the driver could follow another trip's stops.
AfterLaunch is blocked, a toast is shown, and it is logged. Never falls back.
ScheduleActivity.kt

C6 Crashes on empty / malformed data

Beforefirst(), !!, toInt() without guards.
AfterfirstOrNull(), toIntOrNull(), ?: return.
Map/Rep Activity · ViewModel · StatusManager

C7 ANR: MQTT subscribe new

Before"Connection lost" was thrown on the main thread. The main thread died and the UI froze.
AfterSubscribe is guarded. App.kt no longer swallows errors on the main thread.
MqttManager.kt · App.kt

C8 ANR: publish blocks the UI new

BeforeSynchronous MqttClient.publish from the main thread, waiting more than 5 seconds.
AfterPublish/subscribe run on a background thread, timeToWait = 3 seconds.
MqttManager.kt

C9 MQTT "rate limit": sessions kicking each other off new

BeforeThingsBoard allows only one MQTT session per device token. ClientAttributesService and ScheduleActivity (then Map/REP) opened clients with the same Bus token at the same time, so they disconnected each other every 1–2 seconds. The client's fix in c0230d1 (leaked publish loops) was correct, but not sufficient: still 225 disconnects in 6 minutes.
AfterThe service only connects when it needs to publish, then disconnects. Schedule releases its connection while a trip screen is open and reconnects on return. A client that is mid auto-reconnect is now really stopped. Result: 0 disconnects in the same flow.

02 Schedule accuracy fixes

Single status source: centralized thresholds

All thresholds live in ScheduleAdherence.kt. Text, icon, color, marker/zone, and log all use one calculateScheduleStatus() result, in both Map and REP. Delta = scheduled − predicted arrival.

Earlydelta > +30 s
On Time−30 … +30 s
Slightly Behind−300 … −31 s
Very Behind< −300 s

A 10-second hysteresis at each boundary prevents the status from flickering due to GPS noise.

#Problem beforeFix
A1Duplicate thresholds: internal >0 / −300 / −600, UI ±30 / −300. +15 seconds = EARLY internally but "On Time" in the UI.A single ScheduleAdherence module, used by Map and REP.
A2Status flickered due to GPS noise10-second hysteresis
A3Next run used list[1] and could point to the wrong run. The "last run" dialog appeared while a run was still left.nextRunAfterActive() selects the next run explicitly
A4"Next run in 1250 mins", "Late by 1200+ mins"No longer shifted to tomorrow. A difference of more than 4 hours is treated as stale data and shown as "Next run at HH:mm".
A5Late formula jumped: +10 s became "late 10s", −10 s became "late 310s"Shortfall against the minimum layover (300 s, value from the old code)
A6Multiple clocks mixed, midnight not handledOne clock for all calculations. Time parsing is safe across midnight, malformed input is skipped.
A7ETA used straight-line distance. On winding routes the distance actually increased as the bus got closer.Remaining distance measured along the route polyline
A8Fallback speed = distance to the timing point divided by the time of one full tripDivided by the scheduled time to that same timing point. speedSource is logged.
A9Logs were not enough to explain the statusOne ScheduleAdherence line with all inputs and the result, no tokens

08 Needs client confirmation

  1. Meaning of the zone colors. Blue = Slightly Behind (30 seconds to 5 minutes). Previously the marker/zone used blue for 5 minutes or more late. Do the colors carry a specific operational meaning?
  2. 5-minute minimum layover (NEXT_RUN_MIN_LAYOVER_SECONDS). The value comes from the old code. Is this an operational rule?
  3. On Time tolerance of ±30 seconds. If the client uses, for example, ±120 seconds, it only needs changing in one place.
  4. Schedule updates mid-shift require another Fetch Roster.

09 Remaining risks & deferred items

MQTT disconnect/reconnect loop: fixed (C9). The cause was several clients with the same device token disconnecting each other's sessions. After the fix: 0 disconnects on the emulator. Still needs confirming on a physical tablet.

Remaining risks

  • No live test with real GPS on a physical tablet yet.
  • If the roster changes, the real-payload test needs to be rerun.
  • Cancelling via Confirmation is not tested end to end.
  • If the GPS jumps far, the distance estimate can be briefly wrong.
  • Midnight and Very Behind are only covered by unit tests so far.

Deferred (out of scope)

  • Config Data token is hardcoded in MqttManager.kt.
  • vlrskey.jks is committed to the repo.
  • Splash can hang because of the screen recording permission.
  • RepActivity replaces the global crash handler.
  • Duplicated code between Map and REP.
