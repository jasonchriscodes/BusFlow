Quick start in one line: install the APK, grant the permissions, tap Copy AID, put that AID into the bus's config entry in ThingsBoard, reopen the app, then tap Fetch Roster.

2 Install the APK

Before you start: this is a test build (debug-signed). If the tablet already has BusFlow installed from a different build, Android will refuse to update it ("App not installed" / signature conflict). Uninstall the old app first. Uninstalling is safe: the tablet's ID (aid.txt) and the schedule cache are stored in Documents/.vlrshiddenfolder/ and are kept.

Option A: on the tablet (no computer needed)

  1. Copy the APK to the tabletUse a USB cable, Google Drive, or email. Save it somewhere easy to find, such as Downloads.
  2. Open the APKOpen the Files app, go to Downloads, and tap 02_BusFlow-v1.0.1-schedule-stabilization.apk.
  3. Allow installing from this sourceIf Android asks, tap Settings, turn on Allow from this source, then go back.
  4. Tap InstallWhen it finishes, tap Open, or find BusFlow-Publisher in the app list.

Option B: from a computer with ADB

Turn on Developer options → USB debugging on the tablet, connect it with USB, then run:

adb install -r -g 02_BusFlow-v1.0.1-schedule-stabilization.apk

-g grants the normal permissions automatically. You still need to allow "All files access" by hand (next page).

Requirements

Android5.0 or newer (tested on Android 15, tablet 2560×1600)
InternetNeeded for Fetch Roster and live status. Use Wi-Fi the first time: the app downloads a 656 MB offline map on the first Start Route.
StorageAbout 1 GB free
LocationGPS on, set to high accuracy

3 First launch & permissions

Allow everything the app asks for. Without these permissions the schedule cannot be saved or tracked.

PermissionChooseWhy
LocationAllow all the timeLive position, ETA, and Ahead / On Time / Behind
All files accessAllowStores the tablet ID, the schedule cache, the offline map, and logs in Documents/
NotificationsAllowBackground service status
Screen recording promptStart, or CancelOptional trip recording. The schedule works either way.
If "All files access" did not appear, open Settings → Apps → BusFlow-Publisher → Permissions → Files and media (on some tablets: Special app access → All files access) and turn it on.

The start screen

FETCH ROSTERDownloads a fresh schedule from ThingsBoard and starts the day from the beginning. Use it at the start of a shift, or after the schedule was changed on the server.
USE CACHEContinues where the tablet left off (for example after a restart or with no signal). Completed trips stay completed, and an interrupted trip is still at the top.
If the app was closed in the middle of a trip, it goes straight back to the schedule on the next launch. This is expected.

4 Link the tablet to a bus (AID)

Every tablet has a permanent ID called the AID. ThingsBoard uses it to decide which bus (and which schedule) the tablet belongs to. If the schedule does not appear, check this first.

Important: on a new tablet the app may show a "Register" dialog asking for a bus name. Do not tap Register unless you really want to create a brand-new bus. It creates a new device in ThingsBoard and changes the config on every device. Tap Go Offline instead and continue below.
  1. Get the tablet's AIDOn the schedule screen, tap COPY AID (top right) and paste it somewhere, such as a note or a message to yourself.
    With a computer: adb shell cat /sdcard/Documents/.vlrshiddenfolder/aid.txt
    Do not use settings get secure android_id. On Android 8+ it returns a different value from the one the app uses.
  2. Open ThingsBoardGo to Entities → Devices.
  3. Edit the bus entry in every device that has a config For each of Config Data, Bus A Device, and Bus B Device: open the device, go to Attributes → Shared attributes, edit config, find the entry for your bus (for example "bus": "Bus B"), and replace only the aid value with the tablet's AID.
  4. Keep everything else the sameDo not change bus or accessToken. All three devices must end up with the same value.
  5. Reopen the app and tap FETCH ROSTERThe bus's schedule should now appear.
Before
{"aid": "OLD_AID", "bus": "Bus B", "accessToken": "…"}
After
{"aid": "TABLET_AID", "bus": "Bus B", "accessToken": "…"}

The AID is saved in Documents/.vlrshiddenfolder/aid.txt. Reinstalling the app does not change it.

5 Daily use

The schedule screen after Fetch Roster. Green = trip, blue = REP, olive = Sign On / Sign Off / Break.
  1. START ROUTEStarts the first item in the list: Sign On, REP, Trip, or Break.
  2. ConfirmTick the BDC / Hanover confirmation for that item.
  3. DriveThe map shows the route, the upcoming stop, the schedule status, and Next run in.
  4. FinishAt the last stop a Trip Completed dialog shows the rest time before the next run. Tap VIEW NEXT TRIP. For Sign On/Off and Break, tap BACK TO SCHEDULE.
  5. End a trip earlyTap END TRIP (only when the speed is at or below 30 km/h) and enter the passcode (default 0000).
TEST ROUTE runs the same flow with a simulated bus, using the Speed / Slow buttons. Use it for demos and training, not on a live service.
If Start Route shows "No route data for …", the app could not find the right route for that item, so it will not start rather than guide the driver along the wrong route. Tap Fetch Roster again. If it still happens, check busRouteData for that bus in ThingsBoard.

6 Reading the schedule status

The status compares the scheduled time at the next timing point with the predicted arrival (remaining distance along the route ÷ current speed). The text, icon, colour, and stop markers always agree.

StatusPredicted arrival vs scheduleWhat it means
Earlymore than 30 s earlySlow down or wait at the timing point
On Timewithin ±30 sOn schedule
Slightly Behind30 s to 5 min lateA little late
Very Behindmore than 5 min lateSignificantly late

Small GPS jitter does not flip the status: it only changes once the value is clearly past a boundary (10 s margin). When the bus is stopped, the app uses the schedule's average speed for the prediction.

"Late for next run by N mins" appears when the predicted arrival at the last stop leaves less than a 5-minute layover before the next run.
On Time at the start of a trip
Slightly Behind (~1 min late)

7 Checking accuracy with logs

Every status the tablet shows can be traced to the numbers that produced it. Connect the tablet to a computer and run:

adb logcat -s ScheduleAdherence

Each line looks like this:

scheduled=07:34:00 now=07:31:19 distanceRemainingM=1437 effectiveSpeedKmh=20.0 speedSource=GPS predictedArrival=07:35:38 deltaSec=-98 status=SLIGHTLY_BEHIND
distanceRemainingMMetres left to the next timing point, along the route
speedSourceGPS, or SCHEDULE_AVERAGE_FALLBACK when stopped or the GPS speed is implausible
predictedArrivalnow + distance ÷ speed
deltaSecscheduled − predicted. Positive = early, negative = late.

Example check: 1437 m ÷ 5.56 m/s = 259 s, so 07:31:19 + 4:19 = 07:35:38. 07:34:00 − 07:35:38 = −98 s, which is Slightly Behind, the same as the screen.

The app also writes full logs to Documents/Log/ on the tablet.

8 Troubleshooting

ProblemWhat to do
"App not installed"An older build with a different signature is installed. Uninstall it, then install again. The tablet ID and cache are kept.
No schedule / "AID does not match" / Register dialogThe tablet is not linked to a bus. Follow section 4 and check that the AID is identical in config on all three devices.
"No route data for …" on Start RouteTap Fetch Roster again. Check busRouteData for that bus in ThingsBoard.
Start Route does nothing the first timeThe 656 MB offline map is downloading. Stay on the schedule screen on Wi-Fi until it finishes, then try again.
App stays on a blank screen after reopeningForce-stop the app (Settings → Apps → BusFlow-Publisher → Force stop) and open it again.
Status looks wrongCheck the ScheduleAdherence log (section 7): time, distance, speed, and speed source.
A completed trip came backThis should no longer happen. If it does, send us the files in Documents/Log/ and the time it happened.
Known issue, outside this release: during testing, the MQTT connection to ThingsBoard Cloud was repeatedly closed by the server about every 2 seconds. The app no longer freezes when this happens and keeps working, but live updates may be delayed. We suspect the ThingsBoard plan limits or several app connections sharing one device token. Details are in the report.
